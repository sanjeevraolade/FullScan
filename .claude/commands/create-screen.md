Create the **$ARGUMENTS** screen for the FullScan Mobile Platform.

Load `fullscan-architecture`, `fullscan-dynamic-form`, `fullscan-theme-engine`, `fullscan-localization`, and `fullscan-navigation` first.

## First, decide

Should this screen be entirely generated by the Dynamic Form Engine from backend configuration, or does it genuinely need to be a static/hand-built screen (e.g. a workflow container)? Prefer the Dynamic Form Engine whenever the content is configuration-driven — see `fullscan-dynamic-form`.

## Screen responsibilities — nothing more

Render UI, display Runtime data, capture user input, invoke Runtime actions, display validation results (received from the Validation Engine).

## Never implement in a screen

Business logic, workflow execution, validation logic, direct API calls, synchronization, configuration management. If the request requires any of these, route it through the appropriate Runtime Engine instead (`fullscan-runtime-engine`).

## Generate

Screen component, header/body/footer composition, widgets (reuse existing ones — only build new via `/create-widget` if nothing fits), hooks if needed, types, styles via Theme Engine, tests, `index.ts`.

## Non-negotiables

Runtime Context for state (no duplicated state) · light/dark/system theme support · every string localized · accessibility (screen readers, dynamic font, touch targets) · avoid unnecessary re-renders.

## Before finishing, confirm

Runtime integrated · theme and localization supported · accessible · testable and reusable · zero business logic in the screen itself.
